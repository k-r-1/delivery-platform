## 1. 개요

- 맡은 도메인 — 주문(Order), 배송지(Address)
- 추가로 한 일 — 팀 전체 흐름을 한 번에 확인하는 통합 테스트 작성
- 작업 커밋 — 머지 커밋 제외 약 25개
- 쓴 기술 — Spring Boot, Spring Security(JWT), Spring Data JPA, PostgreSQL

간단히 말하면, 주문이 만들어지고 취소되는 전체 과정과 배송지 관리 기능을 담당했다. 특히 결제·정산으로 이어지는 "돈이 오가는 기능"이라, 잘못된 요청·권한 없는 접근·데이터 조작을 막는 부분을 깊게 고민했다.

---

## 2. 구현 기능

### 배송지 (Address)
- 배송지 등록 / 목록 조회(검색·페이징) / 수정 / 삭제
- 기본 배송지는 항상 1개만 유지 — 새 배송지를 기본으로 지정하면 기존 기본 배송지를 자동 해제한다.
- 내 배송지만 수정·삭제 가능 — 요청자와 배송지 주인이 같은지 확인한다.
- 삭제는 데이터를 실제로 지우지 않고 "삭제됨" 표시만 남기는 방식(soft delete)으로 처리했다.

### 주문 (Order)
- 주문 생성 시 가게 상태·영업시간 → 배송지 소유권 → 메뉴 유효성·가격 → 최소 주문 금액을 순서대로 확인한 뒤에만 주문을 받는다.
- 주문 상태를 정해진 순서로만 바꿀 수 있게 했다: `주문요청 → 수락 → 조리 → 배송 → 배송완료 → 완료` (관리자는 예외적으로 강제 변경 가능).
- 주문 취소는 5분 규칙 — 손님은 주문한 지 5분 이내, 가게가 수락하기 전에만 취소할 수 있다.

## 3. 트러블슈팅 & 기술적 의사결정

각 항목은 `현상 → 원인 분석 → 대안 검토 → 해결 → 결과 → 배운 점` 순서로 정리했다.

### 3-1. 권한을 뺏겼는데도 계속 주문이 되는 문제

- **현상.** 관리자가 어떤 사용자를 차단하거나 권한을 낮춰도, 그 사용자가 예전에 받은 토큰으로 계속 주문을 넣을 수 있었다.
- **원인 분석.** JWT는 무상태(stateless)라, 한 번 발급되면 만료 전까지 그 자체로 유효하다. 서버는 토큰 안의 정보만 믿기 때문에 발급 이후 DB에서 권한이 바뀐 걸 알 수 없었다.
- **대안 검토.**
  - ① 토큰 만료 시간을 아주 짧게 → 자주 재로그인해야 해서 UX가 나쁘고, 짧은 창 동안은 여전히 뚫린다. (근본 해결 X)
  - ② 모든 요청에서 DB로 권한 재조회 → 정확하지만 모든 API에 DB 부하가 걸린다.
  - ③ 민감한 도메인에서만 DB 재검증 → 부하를 최소화하면서 위험한 지점을 막는다. ← 채택
- **해결.** 결제로 이어지는 주문·배송지 요청에서만, 토큰 권한을 DB의 실제 권한과 대조하는 `validateUserRoleFromDB()`를 넣었다. (`OrderServiceV1.java:49`, `AddressServiceV1.java:35`)
- **결과.** 손님 권한을 관리자로 몰래 바꾼 뒤 주문을 시도해도, 토큰이 살아있는 상태에서 바로 403(권한 없음)으로 차단됨을 통합 테스트로 확인했다.
- **배운 점.** stateless 인증은 편하지만 "실시간 상태 변화"에 약하다. 보안과 성능은 트레이드오프라, 도메인 중요도에 따라 선택적으로 강한 검증을 거는 게 현실적이다. (트래픽이 커지면 권한 정보를 Redis에 캐싱해 부하를 더 줄일 수 있다.) → [블로그 #171](https://k-r-1.tistory.com/171)

### 3-2. 메뉴 가격이 바뀌면 과거 주문 금액도 흔들리는 문제

- **현상.** 가게가 메뉴 가격을 바꾸면, 이미 완료된 과거 주문의 결제 금액까지 영향을 받을 수 있었다. 또 클라이언트가 가격을 조작해 싸게 주문할 여지도 있었다.
- **원인 분석.** 주문이 메뉴 가격을 그때그때 참조하는 구조면, 주문 이력이 "현재 메뉴 값"에 종속된다. 이력성 데이터인데 값이 고정돼 있지 않은 게 문제였다.
- **대안 검토.**
  - ① 메뉴 가격 변경 이력 테이블을 따로 관리 → 정확하지만 구조가 복잡해지고 조회 때마다 조인 부담이 생긴다.
  - ② 주문 시점 가격을 주문 항목에 복사해서 저장(스냅샷) → 단순하고, 주문 이력이 메뉴 변경과 완전히 독립된다. ← 채택
- **해결.** 주문 항목(`OrderItem`)에 주문 당시 가격을 복사해 저장(`priceAtOrder`)하고, 주문 생성 시 클라이언트가 보낸 가격을 DB의 실제 메뉴 가격과 대조해 다르면 거부했다. (`OrderServiceV1.java:110`)
- **결과.** 이후 메뉴 가격이 바뀌어도 과거 주문 금액은 그대로 보존되고, 가격 위조 주문은 생성 단계에서 차단된다.
- **배운 점.** "그 시점의 사실"이 중요한 이력성 데이터는, 참조가 아니라 복제(스냅샷)해야 안전하다. → [블로그 #179](https://k-r-1.tistory.com/179), [#182](https://k-r-1.tistory.com/182)

### 3-3. 결제 끝난 주문까지 지워지는 문제 (soft delete)

- **현상.** ① 삭제한 배송지·주문이 여전히 목록에 보였다. ② 배송·정산까지 끝난 주문도 삭제·상태변경이 되어버렸다.
- **원인 분석.** 삭제를 물리적으로 지우지 않고 "삭제됨" 표시만 하는 soft delete인데, 조회 쿼리가 그 표시를 걸러주지 않았고, 삭제 가능 여부를 상태로 검증하지 않았다.
- **대안 검토.**
  - ① 하드 삭제로 전환 → 과거 주문·정산이 참조하던 데이터가 사라져 무결성이 깨진다. (탈락)
  - ② soft delete 유지 + 조회 필터링 → 참조는 보존된다. 그럼 필터를 어디서? 서비스마다 수동으로 붙이면 빠뜨리기 쉬우니, 리포지토리 메서드 이름 레벨(`...IsDeletedFalse`)에 강제하는 쪽을 택했다. ← 채택
- **해결.** 조회 메서드에 `IsDeletedFalse` 조건을 일괄 적용하고, 배송완료·완료 상태 주문은 삭제·변경을 막는 방어 로직을 넣었다. (`OrderServiceV1.java:315`)
- **결과.** 삭제한 데이터가 더는 노출되지 않고, 이미 끝난 주문을 되돌리는 잘못된 요청도 막혔다.
- **배운 점.** soft delete는 삭제 로직 하나로 끝나는 게 아니라 모든 조회 경로에 필터가 강제되어야 안전하다. 그리고 삭제 규칙은 "지금 이 순간"이 아니라 정산까지 이어지는 전체 생명주기 관점에서 정해야 한다. → [블로그 #184](https://k-r-1.tistory.com/184)

### 3-4. 상태 규칙이 여기저기서 깨질 수 있는 문제

- **현상.** 주문 상태 전이(요청→수락→조리…) 규칙을 서비스 코드에만 두면, 다른 진입점에서 상태를 직접 바꿀 때 규칙이 무시될 수 있었다.
- **원인 분석.** 규칙(불변조건)이 데이터를 가진 객체(엔티티) 밖에 흩어져 있으면, 그 규칙을 거치지 않는 경로가 언제든 생길 수 있다.
- **대안 검토.**
  - ① 서비스마다 상태 검증을 반복 작성 → 코드가 중복되고, 새 기능에서 빠뜨리기 쉽다.
  - ② 상태 전이 규칙을 엔티티 안으로 캡슐화(리치 도메인 모델) → 어디서 호출하든 규칙을 무조건 거친다. ← 채택
- **해결.** 상태 전이 규칙을 `OrderEntity` 안에 넣었다. `updateStatus()`는 `switch`로 허용된 전이(예: PENDING→ACCEPTED)만 통과시키고 나머지는 `IllegalStateException`을 던진다. `updateRequest()`도 PENDING이 아니면 거부한다. 서비스는 이 메서드를 호출만 하고, 도메인이 던진 예외를 API용 예외(`CustomException`)로 번역한다. (`OrderEntity.java:80`, `OrderServiceV1.java:290`)
  - 단, "5분 이내 취소" 같은 시간 기반 정책은 서비스 계층에 두었다(`OrderServiceV1.java:234`, `Duration.between()`). 요청 시각과 비교하는 응용 로직이라, 엔티티가 항상 지켜야 하는 불변조건과는 성격이 다르다고 판단했다. (엔티티의 `cancelOrder()`는 상태 변경만 담당)
- **결과.** 잘못된 상태 전이는 엔티티 선에서 막히고, 상태 규칙이 한 곳에 모여 유지보수가 쉬워졌다.
- **배운 점.** 데이터의 불변조건은 그 데이터를 가진 객체가 직접 지키게 하고, 서비스는 흐름을 조율한다. 다만 "무엇을 엔티티에, 무엇을 서비스에 둘지"는 규칙의 성격(내재적 불변조건 vs 시간·요청에 의존하는 응용 정책)에 따라 나눠야 한다는 것도 배웠다. → [블로그 #173](https://k-r-1.tistory.com/173), [#183](https://k-r-1.tistory.com/183)

### 3-5. 인가를 한 겹이 아니라 여러 겹으로 (Defense in Depth)

- **현상 & 문제.** 권한 체크를 한 곳에서만 하면, 그 한 곳이 뚫리거나 우회되는 순간 그대로 사고로 이어진다. 결제와 이어지는 주문에서는 특히 위험하다.
- **원인 분석.** 인증(로그인 여부), 인가(역할), 소유권(내 데이터인지), 실시간 권한 변화는 서로 다른 종류의 위협인데, 한 지점에서 한꺼번에 막으려 하면 빈틈이 생긴다.
- **대안 검토.** 컨트롤러에서만 막기 / 서비스에서만 막기 → 둘 다 단일 지점에 의존한다. 대신 역할이 다른 여러 계층이 겹겹이 확인하도록 나눴다. ← 채택
- **해결.** 방어선을 계층별로 나눴다.

  | 계층 | 막는 위협 | 방법 |
  | --- | --- | --- |
  | 컨트롤러 | 역할 없는 접근 | `@PreAuthorize("hasAnyRole(...)")` |
  | 컨트롤러 | 신분 위조(BOLA) | `@AuthenticationPrincipal`로 토큰에서 사용자 정보를 꺼냄 (클라이언트가 보낸 ID를 안 믿음) |
  | 컨트롤러 | 대량 조회 공격 | `PageUtil.validatePageSize()`로 과도한 페이지 크기 차단 |
  | 서비스 | 실시간 권한 변화 | `validateUserRoleFromDB()`로 DB의 실제 권한 재확인 (→ 3-1) |
  | 서비스·리포지토리 | 남의 데이터 접근 | 소유권 확인 + 역할별 쿼리 분리(고객=`findAllByUserId`, 점주=`findAllByStoreId`)로 DB 단계에서 데이터 격리 |

- **결과.** 한 계층을 통과해도 다음 계층에서 다시 걸린다. 각 방어선이 실제로 동작하는지 통합 테스트로 확인했다.
- **배운 점.** 보안은 "한 방"이 아니라 "여러 겹"이다. 각 계층이 서로 다른 종류의 위협을 나눠 막게 설계하면 훨씬 튼튼해진다. → [블로그 #172](https://k-r-1.tistory.com/172), [#180](https://k-r-1.tistory.com/180), [#185](https://k-r-1.tistory.com/185)

## 4. 팀 전체 통합 테스트

내 도메인뿐 아니라 팀 전체가 만든 기능이 하나로 잘 이어지는지 확인하는 통합 테스트(`FullDomainIntegrationTest`, 약 500줄)를 작성했다. 회원가입 → 가게·메뉴 등록 → 주문 → 결제 → 리뷰 → 평점 갱신까지 실제 사용자가 쓰는 순서 그대로 검증하고, 위에서 만든 안전장치(권한 실시간 차단, 5분 취소, 숨김 처리, soft delete)도 함께 확인한다.

여기서도 같은 방식으로 문제를 풀었다.

- **현상.** 통합 테스트가 너무 느리고 코드가 길었다.
- **원인 분석.** 테스트에 필요한 준비 데이터(회원·가게·메뉴)까지 전부 API 호출로 만들다 보니, 검증하려는 것과 무관한 호출이 잔뜩 끼어들었다. 또 5분 취소 규칙은 검증하려면 원칙적으로 5분을 기다려야 했다.
- **대안 검토.**
  - ① 전부 API 호출(순수 E2E) → 실제 사용자 흐름과 가장 비슷하지만 느리고 복잡하다.
  - ② 전부 Repository로 데이터 주입 → 빠르지만 실제 엔드포인트(컨트롤러·보안)를 못 거친다.
  - ③ 하이브리드 → 준비 데이터는 Repository로 바로 주입(`createStoreFixture()` 등), 진짜 검증할 부분만 실제 API 호출. ← 채택
  - 시간 의존 규칙은 5분 실제 대기 대신 `ReflectionTestUtils`로 생성 시각을 조작해 즉시 검증.
- **해결 & 결과.** 하이브리드 구조로 바꾼 뒤 테스트가 빨라지고, "무엇을 검증하는 테스트인지"가 훨씬 명확해졌다. 시간 조작 덕분에 5분 규칙도 기다림 없이 검증했다.
- **배운 점.** 통합 테스트에서 "준비(setup)"와 "검증(assert)"을 분리하면 속도와 가독성을 둘 다 잡을 수 있다. → [블로그 #187](https://k-r-1.tistory.com/187)

## 5. 한계와 후속 과제

## 6. 추가 리팩토링 — 권한 검증 로직 공통화 (프로젝트 이후)

- **문제.** 실시간 권한 재검증 로직(`validateUserRoleFromDB`)이 주문·배송지 서비스에 각각 ~16줄씩 동일하게 중복돼 있었다.
- **해결.** 이 로직을 `UserRoleValidator` 공통 컴포넌트로 추출하고, 두 서비스는 주입받아 호출하도록 변경했다.
- **결과.** 서비스 코드 순 36줄 감소, 인가 정책 일원화. 기존 보안 테스트를 유지한 채 검증기 전용 테스트 4개를 추가해 관련 단위테스트 20개 통과.
- **부가 수정.** 권한 불일치 응답이 의미상 맞지 않게 401(Unauthorized)로 나가던 것을 403(Forbidden)으로 바로잡아, 인증 실패(401)와 인가 실패(403)를 명확히 구분했다.
- **대안 검토.** AOP 어노테이션(`@ValidateDbRole`)도 고려했으나, 인가는 이미 `@PreAuthorize`(AOP)로 처리 중이고 순수 단위테스트에서 검증이 어려워지는 점을 고려해, 단순하고 검증 가능한 컴포넌트 추출을 택했다. Port/Adapter 도입까지는 이 프로젝트의 실용적 DDD 컨벤션 대비 과설계로 판단했다.
